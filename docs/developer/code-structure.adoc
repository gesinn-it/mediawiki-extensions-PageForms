The authoritative overview of the codebase layout is the source tree on
link:https://github.com/gesinn-it/mediawiki-extensions-PageForms[GitHub].
The sections below describe the top-level directories and their purpose.

== Directory layout

`includes/`::
Core PHP classes: utilities (`PF_Utils.php`, `PF_ValuesUtils.php`), the
autoedit API (`PF_AutoeditAPI.php`), and the autocomplete API
(`PF_AutocompleteAPI.php`). The form printer, form field model, and template
model have moved to `src/` (`FormPrinter.php`, `FormField.php`,
`Template.php`); see the `src/` entry below.

`includes/forminputs/`::
One class per input type (e.g. `PF_TextInput.php`, `PF_DateInput.php`,
`PF_CheckboxInput.php`). Each class extends `PFFormInput`.

`includes/parserfunctions/`::
Parser function implementations (e.g. `PF_FormInputParserFunction.php`,
`PF_FormLink.php`, `PF_AutoEdit.php`).

`specials/`::
Special page implementations: `PF_FormEdit.php`, `PF_RunQuery.php`,
`PF_MultiPageEdit.php`, `PF_Forms.php`, `PF_Templates.php`,
`PF_UploadWindow.php`.

`libs/`::
JavaScript modules loaded by ResourceLoader.

`skins/`::
CSS stylesheets.

`languages/`::
i18n JSON files and PHP aliases/magic word definitions.

`src/`::
PSR-4 autoloaded classes under the `MediaWiki\Extension\PageForms\`
namespace. `includes/` and `specials/` are being migrated here
incrementally; see xref:psr4-migration.adoc[PSR-4 Migration Guide] for the
target layout and conventions.

`src/TemplateText/`::
The wikitext of a template that Special:CreateTemplate and Special:CreateClass create.
`Template::createText()` calls the hook `PageForms::CreateTemplateText` and hands the rest to
`TemplateWikitextWriter`. The markup of the display formats (`standard`, `infobox`, `plain`,
`sections`) is one `TemplateFormat` class each; `InternalObjectCall` and `SetCall` build the
calls that store the fields. `TemplateFieldParser` does the reverse: it finds the fields of a
template in its text, and `Template` loads the text and keeps the result.

`tests/`::
PHPUnit and QUnit test suites.

== Characterization tests of the form printer

`tests/phpunit/integration/src/FormHtmlCharacterizationTest.php` renders form definitions with
`FormPrinter::formHTML()` and compares everything it returns with a snapshot in
`tests/phpunit/integration/golden/formhtml/`.

The snapshots are a safety net for refactoring, not a specification. They record what the code
produced when they were written, so that a change of structure can be shown to leave the output as
it was. They do not say that the output is right: a snapshot can hold behaviour that was wrong at
the time. For example, the snapshot of a `checkboxes` field with a `mapping template` on an existing
page first recorded that no box was checked; that was fixed later and the snapshot changed with the
fix. To find out what a form should do, read the documentation and the tests of the input type, not
the snapshot.

A case that is known to record a defect carries a `known defect` key naming the issue or commit, and
its snapshot is updated in the commit that fixes the defect. At the moment no case is marked: the
only one so far was the checkboxes case above.

To update a snapshot deliberately, run the test with `PF_UPDATE_GOLDEN=1`, review the diff of the
files in `golden/formhtml/` (every changed line has to be explained by the change you made) and
commit them together with that change. Never record the snapshots again just to make a failing run
green.

== Characterization tests of the created template text

`tests/phpunit/integration/src/TemplateTextCharacterizationTest.php` writes the wikitext of
templates with `Template::createText()` and compares it with a snapshot in
`tests/phpunit/integration/golden/templatetext/`, for every display format and for fields of every
kind. The same rules as for the snapshots of the form printer apply: they record what the code
wrote, they do not say that it is right, and they are recorded again with `PF_UPDATE_GOLDEN=1`
only for a change that is meant.

One snapshot records a defect: for a field in the main namespace, the calls of `#set`,
`#set_internal` and `#subobject` get `0:` in front of the field parameter.

`tests/phpunit/integration/src/TemplateFieldsCharacterizationTest.php` does the same for the
reverse, the fields that `TemplateFieldParser` finds in the text of a template, with snapshots in
`golden/templatefields/`. It records two quirks: a field whose name is not followed by `|` gets the
key 0 and replaces another field with that key, and names that are numbers are compared loosely.
