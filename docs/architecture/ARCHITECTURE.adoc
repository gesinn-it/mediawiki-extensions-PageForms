= PageForms Architecture
:toc:

== Overview

PageForms is a MediaWiki extension that provides structured editing capabilities for wiki pages.

Instead of editing raw wikitext, users interact with forms that generate the corresponding page content based on predefined templates.

Forms are defined in the *Form namespace* and describe:

* templates used to generate content
* fields mapped to template parameters
* input widgets used for editing
* constraints and validation rules

The PageForms architecture transforms these form definitions into interactive HTML forms and ultimately into generated wiki text.

== Architectural Layers

PageForms can be understood as a pipeline consisting of several layers.

----
Form Definition (Form namespace)
        │
        ▼
Form Definition Model (value-free)
        │
        ├─────────────────────────────┐
        ▼                             ▼
Interactive Form             PF_AutoeditAPI
(FormPrinter + JS)           (API / #autoedit)
        │                             │
        │                     Values (page + request)
        │                             │
        └──────────────┬──────────────┘
                       ▼
           Submission Processing
                       │
                       ▼
           Wiki Page Generation
----

Each stage is handled by specific components within the extension.

At the *form definition model* stage the pipeline forks into two paths:

* *Interactive path* — `FormPrinter` renders the form as HTML, ResourceLoader
  modules initialize client-side widgets, and the user submits the form via the
  browser.
* *API path* — `PF_AutoeditAPI` (invoked directly via the MediaWiki API or
  through the `#autoedit` / `#autoeditrating` parser functions) applies field
  values programmatically, without any browser interaction. It reads the values
  of the existing page through `FormDefParser` and `FormValues` (no HTML
  round-trip), lays the request over them, and then proceeds to submission
  processing.

== Core Domain Model

The model is split in two layers: what a form *is* (the form definition, free of
any value) and what it *holds* (values from a page or a request). A third group of
classes, which combines the two with the environment of one request, exists for
rendering.

=== Form definition model (value-free)

Namespace `MediaWiki\Extension\PageForms\FormDefinition`.

A single `FormDefinitionReader` reads the `{{{...}}}` tags of a form definition into
a `FormDefinition`: an ordered list of elements (`TemplateSpec`, `FieldSpec`,
`SectionSpec`, `StandardInputSpec`, `InfoSpec`, `EndTemplateSpec`, `UnknownTagSpec`
and the `TextSpec` between them). It is the only tokenizer
(`FormDefinitionReader::findNextTag()`); `FormCache`, `FormPrinter::render()` and
`FormDefParser` all use it.

`FormCache` stores the model (as an array, see `FormDefinition::toArray()`), keyed by
form page, a format version and parser options. When the stored format changes the
version is raised: older entries are never read, the definition is rebuilt on the next
request, and the old entries are removed when the form is purged.

=== Values layer

`FormValues` holds the values of the fields per template and instance, the
parameters the form does not define (kept with their instance), the free text and
the fields whose value is a label that has to be mapped back (`mapping template`,
`mapping property`).

* `FormDefParser::readPageValues()` fills it from the text of an existing page
  using the form definition model. `TemplatePageValues` reads one template call from
  the page text (bracket-aware, no MediaWiki state); `FormPrinter::render()` uses the
  same class through `TemplateInForm`, so both read a page in the same way.
* `FormValues::mergeRequest()` applies a request on top: request values win,
  `+=` / `-=` modifiers and `Template[<n>][field]` instance numbers are resolved
  against the values of the page.
* `RestrictedInputs` lists the fields, sections and the free text a user may not
  change (`restricted`); they are removed from a request before it is applied.

=== Rendering classes

Used by `FormPrinter::render()`; they mix structure, request state and values.

* `TemplateInForm` — a template used within a form: mapping template parameters to
  form fields, template multiplicity, template-level configuration.
* `FormField` — a field of the form for the current request: field configuration,
  input type selection, default values, value sources and the possible values
  (including the labels of `mapping template` and `mapping property`, which
  `MappingLabels` provides).
* `MappingLabels` — the labels a field shows for its values. The labels of a mapping
  template are expanded in batches and remembered per template revision; the memory
  belongs to the object, which `FormPrinter` creates once and hands to its fields.
* `TemplateField` — a field defined in the underlying template: property mapping,
  field type, possible values, delimiter rules.

`Form` is only used by `Special:CreateForm`, to describe a form that is being
created; it is not the model of a form definition.

== Form Processing Pipeline

When a form page is accessed, the following processing steps occur.

----
Form definition page
        │
        ▼
FormCache: FormDefinition (read by FormDefinitionReader on a miss)
        │
        ▼
FormPrinter::formHTML() walks the elements
        │
        ▼
TemplateInForm / FormField objects created
        │
        ▼
HTML of the form
----

The reading stage turns the form markup into the value-free model once; rendering
then walks its elements and builds the request-dependent objects.

== Form Rendering

Rendering of forms is handled primarily by:

----
FormPrinter
----

Responsibilities include:

* generating the HTML structure of the form
* initializing input widgets
* attaching client-side behavior
* preparing submission metadata

The renderer transforms the form definition model and the values into the interactive
form presented in the browser. `PF_AutoeditAPI` also calls it, without sending
the HTML anywhere, to produce the wikitext of the page from the submitted values.

== Programmatic Editing (API Path)

`PF_AutoeditAPI` is a MediaWiki API module that allows pages to be created or
updated without user interaction.

Entry points:

* Direct MediaWiki API call: `action=pfautoedit`
* `#autoedit` parser function (inline links or buttons on wiki pages)
* `#autoeditrating` parser function (star-rating widget)

Behavior:

* Accepts form name, target page, and field values as request parameters.
* Reads the values of the existing page with `FormDefParser::readPageValues()`,
  applies the request with `FormValues::mergeRequest()` and drops what the user
  may not change (`RestrictedInputs`). Earlier versions rendered the form and
  extracted the values from its HTML (`HtmlFormDataExtractor`); that route is now
  only used to show an existing page in the form editor.
* Bypasses the browser UI entirely — no HTML form is sent to the client.
* Saves the page via the standard MediaWiki edit pipeline, based on the revision
  that is current when the page text is read (so a change made in between is
  merged or reported as an edit conflict).

This makes `PF_AutoeditAPI` the primary integration point for automated or
inline page updates triggered from wiki pages or external scripts.

== Page Generation Pipeline

When a form is submitted, PageForms generates wiki text representing the content of the page.

The generation pipeline looks like this:

----
Form submission
        │
        ▼
Field values collected
        │
        ▼
Template calls constructed
        │
        ▼
Wiki text generated
        │
        ▼
Page saved via MediaWiki
----

Key class involved:

----
PFWikiPage
----

This class manages the generation and updating of page content based on form submissions.

== Input System (Plugin Mechanism)

PageForms supports a flexible *input system* allowing different types of form widgets.

Examples include:

* text inputs
* dropdowns
* checkboxes
* comboboxes
* date pickers

Input types are defined through the parameter:

----
input type=
----

Example:

----
{{{field|Author|input type=combobox}}}
----

Internally, PageForms resolves input types using a *plugin mechanism*.

Input widgets are implemented as separate components that receive configuration arguments and render their HTML representation.

This architecture allows extensions to introduce additional input types without modifying the core PageForms logic.

See xref:input-types.adoc[Input Type System] for the full documentation.

== Client-Side Architecture

PageForms uses JavaScript to enhance the interactive behavior of forms.

Client logic is implemented using ResourceLoader modules.

Key JavaScript components include:

----
PageForms.js
PF_validation.js
PF_showOnSelect.js
PF_multipleInstance.js
PF_formInput.js
----

Responsibilities of the client layer include:

* widget initialization
* form validation
* dynamic field behavior
* asynchronous interactions

The client layer interacts with MediaWiki APIs where necessary.

See xref:input-types.adoc[Input Type System] for widget initialization details and
xref:autocomplete.adoc[Autocomplete Subsystem] for asynchronous interactions.

== Integration with MediaWiki

PageForms integrates deeply with MediaWiki through several mechanisms.

=== Special Pages

Special pages provide entry points for form interaction.

Examples include:

----
Special:FormEdit
Special:RunQuery
----

=== Parser Functions

PageForms provides parser functions that allow forms to be embedded in wiki pages.

Examples include:

----
#forminput
#formlink
#autoedit
----

These functions act as the primary interface between normal wiki pages and PageForms functionality.

=== Hooks

The extension registers MediaWiki hooks for:

* form rendering
* page editing integration
* parser behavior

These hooks enable PageForms to integrate with the MediaWiki editing workflow.

== MediaWiki Version Compatibility

PageForms supports a range of MediaWiki versions. Where the MW or PHP API
differs between versions, the compatibility gap is encapsulated in a static
helper on `PFUtils` rather than repeated at each call site:

[source,php]
----
// DB reads — use the centralized helper:
$db = PFUtils::getReplicaDB();

// WikiPage from Title — use the centralized helper:
$wikiPage = PFUtils::newWikiPageFromTitle( $title );
----

These helpers contain the version gate internally and shield all other code
from knowing which MW version is running.

Test infrastructure notes:

* `phpunit.xml.dist` sets `convertWarningsToExceptions="true"` — any
  `E_WARNING` or `E_DEPRECATED` on PHP 8 becomes a test exception. Null values
  passed to string functions must be guarded before reaching PHP 8 code.
* MW 1.43 test bootstrap sets `$wgArticlePath = '/wiki/$1'`. JSONScript tests
  that assert URL paths must pin `wgArticlePath` in their `settings` block.
* MW 1.43 ooui uses Web Components — `global.HTMLElement = window.HTMLElement`
  must be set in the node-qunit `setup.js`.
* Driving a full OOUI `WindowManager`/`ProcessDialog` open/close cycle in
  node-qunit requires `oojs-ui-windows.js` (not loaded by default), plus
  `global.navigator` and a `requestAnimationFrame`/`cancelAnimationFrame`
  stub — none of these are provided by this repo's jsdom version. All are
  set up once in `setup.js`.

== Known Architectural Issues

PageForms has evolved over many years and contains some legacy architectural patterns.

Examples include:

* `TemplateInForm` and `FormField` mix the structure of a form with the state of one
  request and with values; only the form definition model and `FormValues` are free
  of that
* historical coupling with specific extensions
* global configuration variables influencing runtime behavior

Future refactoring could focus on improving separation of concerns and modularization.
Deliberately left open for now:

* `FormPrinter::render()` is about 690 lines and does the rendering of a whole form in one
  method; splitting it is a refactoring of its own.
* The FORMEDIT branch of `PFAutoeditAPI` still gets the values of an existing page from
  `formHTML()` and `HtmlFormDataExtractor`. Moving it to `readPageValues()` would change which
  values `mOptions` holds (defaults, query values, mapping labels) and is a change in
  behaviour, not only in structure.
* `remote autocompletion` together with a `mapping template` still returns labels from the API.
